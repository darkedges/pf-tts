# Isolated PingAuthorize 11.1

This chart owns the WAI decision point in namespace `wai-pingauthorize`. It is
the policy decision point for the strict call chain and holds no identity of its
own.

The product image is referenced by digest with no tag. PingAuthorize publishes on
the moving `edge` tag, which cannot be pinned to a reviewed build; the digest can.

## The policy must be the reviewed one

The vendor's `getting-started/pingauthorize` server profile is fetched at startup
and ships a permissive sample policy. The reviewed policy is applied over it by a
`30-` dsconfig in the `/opt/in` overlay.

That overlay cannot be mounted as a ConfigMap directly. A ConfigMap volume is a
farm of symlinks into a timestamped directory, and the product's entrypoint
copies `/opt/in` into staging without following them — so the overlay disappears
silently and the vendor's sample policy stays in force. The result is a decision
point that starts healthy, serves the right certificate, and permits everything.

An init container therefore materialises the overlay as real files and fails if
the reviewed dsconfig is not among them. When verifying a deployment, check the
`deploymentPackageId` in a decision response: it must be the reviewed package,
not the vendor's.

## Serving identity

The certificate is generated by `scripts/import-pingauthorize-11-1-to-vault.ps1`
and delivered from Vault, rather than left to the product's self-signed setup
certificate. That one names the container hostname, which here is the pod name
and not the Service name the gateway addresses, and the adapter refuses both
disabled verification and a `ServerName` override.

The private key and the public certificate are separate Vault records. The strict
gateway's policy grants it the public one only.

## Install

```text
kubectl create namespace wai-pingauthorize
helm upgrade --install wai-pingauthorize deploy/helm/wai-pingauthorize --namespace wai-pingauthorize
```

Prerequisites: the Vault records imported, the `wai-vault-server-ca` bootstrap
Secret present in the namespace, and the `hostpath` storage class.

## Trust boundary

The decision point performs no client authentication: the adapter sends no
credential and trust is one-way TLS plus reachability. The NetworkPolicy is
therefore the access boundary, not a defence-in-depth extra. Only the namespaces
in `decisionIngressNamespaces` may reach port 1443, and the LDAP port is not
published at all.
